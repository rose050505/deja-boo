Reviewer: functional review on three public repos the project never tuned on (pallets/click 3,416 commits, psf/black 2,525, koajs/koa 1,328; full history; replayed real revert/restore commits and random ordinary commits through the PreToolUse and Stop hooks). Core result: blocks of ≥4 lines that come back are caught 8 of 9 times, and ordinary writes fire about 1 in 212 (0.5%). Seven defects to fix. Record them as "post-review fixes 3" in the affected specs' tasks.md (revenant-watch and graveyard-miner), with the numbers below, then implement. Keep every existing property test passing; add properties where noted.

1. **Hook latency on large files (must).** One write to click `src/click/core.py` (4,018 lines) takes 4.0–5.7 s; black `tests/test_black.py` 14.5 s; a 120k-line file 11.9 s; Stop up to 15.7 s. CPU profile of `check core.py` (4.6 s): `kgramWinnow` 2.5 s, `normalizeBlock` 0.5 s — `indexWindows` re-normalizes and re-fingerprints every window from scratch for every tombstone width. Fix: tokenize/hash each line once and slide windows over the precomputed k-gram hashes (or score only windows that overlap added lines). Target: ≤500 ms for a 4,000-line file on this machine; add a benchmark test like the existing latency one. Results must not change (property: new windowing == old windowing on random inputs).
2. **Comment fragments matched as code (must).** In koa, a new file containing only a common JSDoc block (`Return request header. / @return {Object} / @api public`) is blocked with Similarity 1.00 against c699c75; `check` on the unchanged `lib/request.js` also blocks. Cause: when the deleted hunk doesn't include the opening `/*`, the comment interior is normalized as code. Fix: drop deleted blocks whose lines are all comment-like (`*`, `/*`, `*/`, `//`, `#` lines and blank), and use the pre-deletion file context to know whether a hunk is inside a block comment when that is cheap. Property: a block made only of comment lines never becomes a tombstone.
3. **Tiny fingerprints fire on idioms (must).** Tombstones with only 1–3 winnowed hashes: click 38, black 32, koa 8. Writing a py2 idiom `try: range_type = xrange …` into a new file warns (and the hook blocks with exit 2) against an unrelated "apply reorder-python-imports" tombstone; black's `include_regex, exclude_regex, extend_exclude_regex, force_exclude_regex,` argument list blocks. 3 of 3 targeted probes were false alarms. Fix: a tombstone needs at least 4 distinct hashes to be watched (configurable `minHashes`, default 4); measure how many tombstones this drops on the 6 research repos and write it in research/matching-eval.md.
4. **`check` and MCP `check_snippet` alarm on code that is already at HEAD (must).** On unchanged HEAD files: click 17/91 files alarm (8 block), koa 31/83, black 13/400. Cause: there is no `before`, so Revert tombstones alive at HEAD always fire, and code between the alive threshold (0.8) and warn (0.5) fires too. Fix: when checking a path inside the repo, use HEAD's version of the same path as `before` (the hook already has before/after); only report what the new text makes worse. `check --no-head` keeps the old behaviour.
5. **Scattered small deletions are out of scope (document).** Real revert/restore commits replayed: 3 of 18 caught. Misses are reverts spread over many 1–3-line hunks (click 0d1b8ea, six hunks of 1–2 lines) and code lost in merge resolution (`--no-merges`, click c52f43c). Write this limit plainly in README ("What it can't see") with the numbers. No code change required unless you see a cheap, safe way to merge same-commit hunks; if you do it, measure the false-alarm cost first.
6. **New-user path is broken (should).** `deja-boo index` writes `graveyard.json` by default, but `check` and the hooks read `.deja-boo/graveyard.json` → exit 3 "no graveyard". `npm run bury` only indexes this repo. `.kiro/hooks` use the relative `node dist/cli/main.js`, which fails silently (fail-open) in other repos.
